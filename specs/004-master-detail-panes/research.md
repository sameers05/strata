# Research: Master-Detail Pane UI

## Pane-fragment endpoint shape: nested throughout for Group-task, mirroring 003

- **Decision**: Every Group-task pane route — list/drill, blank-create, select, create, update, delete — nests under `/panes/projects/{project_id}/group-tasks/...`, exactly mirroring 003's full-page convention: `GET /panes/projects/{project_id}/group-tasks` (list), `GET /panes/projects/{project_id}/group-tasks/new` (blank create), `GET /panes/projects/{project_id}/group-tasks/{group_task_id}` (select), `POST /panes/projects/{project_id}/group-tasks`, `PUT /panes/projects/{project_id}/group-tasks/{group_task_id}`, `DELETE /panes/projects/{project_id}/group-tasks/{group_task_id}`. There is no flat `/panes/group-tasks/{id}` address for anything.
- **Rationale**: 003 established `get_active_project_or_404` specifically so that every nested Group-task route independently re-verifies its parent Project is still active before touching the Group-task, 404ing otherwise (003's FR-015a) — this is exactly the kind of "existing business rule" this feature's own FR-028 requires stay unchanged. Keeping every route nested lets that same dependency (a `project_id` path parameter feeding `Depends(get_active_project_or_404)`) carry forward into this feature's routers unmodified in spirit: every select/edit/delete route still declares `project: Project = Depends(get_active_project_or_404)` and still 404s on a missing/soft-deleted parent before doing anything else, identical to 003. A flat, id-only address would have no `project_id` in the path for that dependency to key off, silently losing that protection — which is exactly the risk this decision avoids.
- **Alternatives considered**: Flat addressing keyed only on `group_task.id` (an earlier draft of this plan) — rejected. It's true that an *already-active* Group-task's parent is guaranteed active too (the cascade-block invariant: `soft_delete_project` already refuses to delete a Project with active Group-tasks) — so in principle the explicit check on select/edit/delete is provably redundant for rows that are already active. But relying on that invariant to skip the explicit check trades a check that is always independently correct and directly traceable to FR-015a for one whose correctness now depends on a *separate* piece of business logic (the cascade block) never regressing — and it does nothing for the create path, which still needs the parent-active check regardless of this decision. Preserving 003's protection exactly, with an unbroken line back to its own FR-015a rationale, outweighs the one extra dependency-resolved query this costs at this scale.

## Details-pane defaulting is bundled into every left-pane list response, not a separate call

- **Decision**: Every route that re-renders `#left-pane`'s list content (`GET /`, `GET /panes/projects`, `GET /panes/projects/{project_id}/group-tasks`, and the Back control's target) also computes and returns an out-of-band `#details-pane` fragment defaulting to that list's first active item (ordered by `serial_num`) or its create-prompt if empty. This is one response, not two round-trips.
- **Rationale**: FR-019 ("when the left pane drills into a non-empty list, default the details pane to that list's first active item") applies identically whether the list changed because of a drill click, a breadcrumb jump back to an ancestor, the initial home load, or the Back control returning from Deleted Items — it's the same rule every time a list swap happens, not a special case of any one trigger. Bundling it as an OOB fragment in the same response means the client never has to remember to fire a second request, and there's no flash of stale details-pane content between two round-trips.
- **Alternatives considered**: A separate client-side follow-up request to fetch the details-pane default after the list swap lands — rejected, doubles request count for no benefit and introduces a window where the two panes are visibly out of sync.

## Row removal on delete: explicit OOB `hx-swap-oob="delete"`, not `hx-swap="delete"` on the request

- **Decision**: Delete controls declare `hx-swap="none"` (no `hx-target`). The row is removed only via an explicit, conditionally-present out-of-band fragment in the response body — `<tr id="project-row-{id}" hx-swap-oob="delete"></tr>` (or the Group-task equivalent) — included only when the soft-delete actually succeeded.
- **Rationale**: The cascade-block rejection (a Project delete blocked by active Group-tasks, unchanged from 003) is itself a `200` response, because it needs to deliver an OOB `#details-pane` error fragment, and htmx only processes OOB swaps out of a response it treats as successful — the identical "reject with a `200` carrying an OOB error container" pattern this project has used since 001's own validation-error handling (`#form-errors`), later extended to page-level rejections in 001's Phase 6. If the delete control instead used htmx's built-in `hx-swap="delete"` + `hx-target="closest tr"`, htmx would remove the row on **any** `200` it receives — including the cascade-block rejection — regardless of whether the delete actually happened, silently making a blocked delete look like it succeeded from the user's point of view (the row disappears even though nothing was deleted). Making removal an explicit, conditionally-included OOB element ties it to the server's actual decision instead of to the response's HTTP status class.
- **Alternatives considered**: `hx-swap="delete"` + `hx-target="closest tr"` (the initially-drafted approach) — rejected once the interaction with the cascade-block's own `200`-with-OOB-fragment response was worked through; it silently breaks exactly the guarantee FR-014 depends on (a blocked row must never appear to have been deleted). Returning a non-`200` status for the cascade-block rejection instead (e.g. `409 Conflict`) so `hx-swap="delete"` could safely stay tied to `2xx` — rejected, since it would require the OOB `#details-pane` error fragment to be delivered on a non-2xx response, and htmx does not process OOB swaps on error-status responses by default; keeping every response in this contract a `200` and controlling behavior entirely through which OOB fragments are present is simpler and consistent with the rest of this feature's own error-handling conventions.

## FR-017a ("deleted-while-selected" auto-select): concrete read path across pane boundaries

- **Decision**: Not an Alpine store. The details-pane fragment's root element — the `<div id="details-pane" hx-swap-oob="true">` itself, re-sent whole on every swap — always carries `data-entity-type` (`"project"`/`"group_task"`) and `data-entity-id` attributes, absent/empty for the blank-create and empty states (`data-model.md`). Every row's delete control, physically inside `#left-pane` — a separate DOM region from `#details-pane` — declares:

  ```html
  hx-vals='js:{selected_type: document.getElementById("details-pane").dataset.entityType,
                selected_id: document.getElementById("details-pane").dataset.entityId}'
  ```

  `hx-vals`' `js:` prefix is a native htmx capability (not Alpine): the object literal is evaluated as JavaScript fresh, at the exact moment htmx serializes that request. `document.getElementById(...)` resolves against the whole document regardless of which pane the requesting element physically lives in — a plain, synchronous DOM read, not a cached or reactive value, and not something that needs a shared store, custom event, or other cross-component signal to bridge the two panes. The `DELETE` handler receives `selected_type`/`selected_id` as ordinary request parameters and compares them to the entity it just soft-deleted; on a match, the response body additionally contains an out-of-band `#details-pane` swap to the next remaining active item in that same list (or the create-prompt if none remain) — computed by simply re-calling the existing `list_active_projects` / `list_active_group_tasks` function *after* the soft-delete has committed, since the deleted row is now naturally absent and the first remaining item by `serial_num` is exactly what FR-017a asks for. On a mismatch, the response still removes the row (via an explicit OOB `hx-swap-oob="delete"` fragment — not `hx-swap="delete"` on the request itself, see `contracts/pane-mutation-routes.md`'s "Row removal" section for why), but `#details-pane` is untouched.
- **Rationale**: The server is explicitly stateless per request (no session store), so "is the entity I'm deleting also the one currently open in the details pane" cannot be known server-side without the client telling it, and the two panes are separate DOM subtrees with no parent/child relationship a component-scoped read could exploit. A shared Alpine store (`Alpine.store('selection', {...})`, written on every details-pane swap, read from the left pane via `$store.selection.type`) was considered and would work, but it duplicates state that the DOM attributes already hold authoritatively — the store would need its own write step kept in sync with every detail-pane swap, a second source of truth for a value `data-model.md`'s "server-rendered fragment self-description" principle already treats as owned by the DOM alone. A direct `document.getElementById` read has no separate write step to forget and no staleness window: it reads whatever `#details-pane` currently contains at the instant the delete button is clicked. Re-using the existing active-list functions for "what's next" means FR-017a needs zero new query logic — it's the identical "first active item, or create-prompt" rule FR-019 already requires, applied after a delete instead of after a drill.
- **Alternatives considered**: The Alpine-store approach above — rejected per the duplicate-state reasoning. A server-side session/cookie tracking "currently selected entity" — rejected outright, the plan input is explicit that no session store is introduced. A custom DOM event dispatched by the details pane on swap, listened for by a left-pane component and cached there — rejected as more machinery than a one-line `hx-vals` read accomplishes for free. Always including the OOB "next item" swap unconditionally, letting the client discard it if the deleted row wasn't selected — rejected as more response payload for no benefit, and it would incorrectly clobber a details-pane the user had unsaved edits in in a totally unrelated context.

## FR-015 delete-eligibility batching applies for real only to the Project list

- **Decision**: `services.py` gains one new function, `list_active_projects_with_delete_eligibility(session) -> list[tuple[Project, bool]]`, computing each Project's active-Group-task count via a single `LEFT JOIN group_task ... GROUP BY project.id` query (the existing `ix_group_task_project_id` index from 003 already covers the join). The Group-task list's own delete-eligibility batching is not implemented as a real query in this feature — with no Task table to count against, every Group-task row's delete control is simply always enabled. `list_active_group_tasks` itself is unchanged.
- **Rationale**: FR-015 requires "one combined data-fetch rather than a separate fetch per row" for whichever child table actually exists. For Project→Group-task, that table (`group_task`) exists today, so the real batched query is buildable and required. For Group-task→Task, `task` doesn't exist as a table at all (per the spec's FR-006/FR-029 clarification) — there is nothing to batch a query against, and hard-coding "always eligible" is both correct (an entity with no possible children can never have active children) and consistent with FR-029's now-clarified meaning: the *mechanics* must be reusable by Task's future slice, not that Task-shaped eligibility logic is faked in ahead of time.
- **Alternatives considered**: Writing a generic, entity-agnostic "count active children" function parameterized by table/FK-column now, even though only one concrete caller (Project) exists — rejected as speculative generalization with a single real call site; Task's future slice can extract the pattern once a second real caller exists, same reasoning 003's research.md already used to reject a premature shared validation helper.

## "Deleted Items" Back control target: in-memory client store, not localStorage

- **Decision**: An Alpine store (page-lifetime, in-memory only) records the URL of whichever left-pane list fragment (`/panes/projects` or `/panes/projects/{id}/group-tasks`) was most recently rendered, updated via an `htmx:afterSwap` listener scoped to `#left-pane` that skips recording when the swapped-in view is the Deleted Items view itself. The Back control's target is bound to that stored value, defaulting to `/panes/projects` if nothing has been recorded yet (e.g., Deleted Items was the very first action taken after home load).
- **Rationale**: FR-002 already mandates that a browser reload always returns to the home state with "no attempt to restore the prior drill position" — so the Back target has no reason to survive a reload, and an in-memory store is sufficient and simpler than localStorage (which the divider-position requirement, FR-025, genuinely does need to survive reloads).
- **Alternatives considered**: Persisting the last list URL to localStorage alongside the divider position — rejected, would silently contradict FR-002's "no attempt to restore prior drill position on reload" if implemented carelessly (e.g., if a future change also auto-restored drill state on load using the same key). Keeping it in-memory only makes that impossible by construction.

## Dirty-tracking / unsaved-changes navigation guard: one global `htmx:confirm` listener, opt-in via a shared marker attribute

- **Decision**: A single Alpine component at the shell root listens once for the document-wide `htmx:confirm` event (which htmx fires, cancelable, before *every* htmx-triggered request). The handler only acts when the triggering element (`evt.detail.elt`) carries a shared `data-pane-nav` marker attribute. Every row title/View link, breadcrumb link, the "+ New" control, the Deleted Items link, and the Back control carry that marker; the details-pane's own Save button and the divider's drag handle do not, and so are never gated. When a marked element fires and the dirty flag is set, the handler calls the browser's native `confirm()`; on cancel it prevents the request, on confirm (or when not dirty) it lets the request proceed.
- **Rationale**: A single document-level listener plus an opt-in marker is less error-prone than wiring an individual Alpine `@click` handler onto each of the five distinct control types the spec calls out (FR-026) — a future control that needs the same guard (e.g., Task's own future nav links) only needs the marker attribute, not a new handler. It also cleanly avoids the trap of accidentally gating the Save button's own submit request, which would incorrectly ask "discard unsaved changes?" about the very action that saves them.
- **Alternatives considered**: A per-element `@click` handler on every navigation control, as the literal reading of the plan input suggests — functionally equivalent but more wiring surface area (five separate call sites instead of one listener + a shared attribute), and easier to accidentally omit on a newly added control.

## Divider drag + persistence

- **Decision**: An Alpine component on the shell root tracks the left pane's width as a percentage, updates it live on `pointermove` while dragging, and writes it to `localStorage` (`stratapanel-split` or similar key) on drag end. On load, the shell reads that key and applies it inline (via an Alpine `x-init`/`x-bind:style`) before first paint if present, falling back to a 30/70 default otherwise.
- **Rationale**: Matches FR-024/FR-025/SC-006 directly; percentage (not pixel) width survives window resizes sensibly. `localStorage` is the only client-side persistence this feature needs that must survive a reload, since FR-002 explicitly scopes "no restore on reload" to drill/selection state only, not the divider.
- **Alternatives considered**: Persisting the split server-side (a settings table/row) — rejected, explicitly out of scope per the plan input ("client-side-only concern") and Assumptions in spec.md.

## Alpine.js vendoring

- **Decision**: `app/static/alpine.min.js`, checked into the repo, referenced with a plain `<script>` tag in `base.html` alongside the existing `htmx.min.js` and `pico.min.css` `<link>`/`<script>` tags. No CDN, no package manager for frontend assets.
- **Rationale**: Matches the project's existing convention for both prior frontend dependencies (HTMX, Pico.css), established in 001/002 specifically to avoid a runtime external dependency for a self-hosted single-user tool.
- **Alternatives considered**: CDN-hosted Alpine — rejected outright, contradicts the established, explicit convention this feature's own plan input calls out.

## New-row insertion ordering needs no sort-aware logic

- **Decision**: On successful create, the OOB fragment inserting the new row into the left pane's list uses `hx-swap-oob="beforeend:..."` (append to the end of the list body), with no client or server-side re-sort step.
- **Rationale**: `serial_num` auto-assignment (`MAX(serial_num) + 1` among active rows, unchanged from 001/003) guarantees a newly created row's `serial_num` is strictly greater than every existing active row's, and lists are always rendered ordered ascending by `serial_num` — so appending is always equivalent to correctly-sorted insertion. This holds for both Project and Group-task, unchanged by this feature.
- **Alternatives considered**: Re-fetching and re-rendering the entire list on every create (guaranteed-correct order but throws away the cheaper in-place update FR-023 asks for) — rejected as unnecessary given the ordering guarantee above.
