# Research: Group-task Management

## Composite partial-unique indexes scoped by parent Project

- **Decision**: Two partial unique indexes on `group_task`: `UNIQUE(project_id, title) WHERE deleted = false` and `UNIQUE(project_id, serial_num) WHERE deleted = false`, mirroring Project's own `WHERE deleted = false` pattern but adding `project_id` as the leading column so uniqueness is scoped per-parent rather than global.
- **Rationale**: FR-005/FR-006 require title and serial_num uniqueness scoped to the parent Project, not globally — a plain single-column unique index (as Project uses) would incorrectly reject two different Projects' Group-tasks sharing a title or serial_num. The service-layer check-then-write pattern established in 001 (research.md's "Rationale" for title/serial_num uniqueness) still does the primary rejection-with-a-clean-message work; these composite indexes are the same belt-and-suspenders backstop against races, just with one more column.
- **Alternatives considered**: A single global unique index on `title` alone (or `serial_num` alone) — rejected, contradicts FR-005/FR-006 outright. Enforcing uniqueness only in the service layer with no DB-level backstop — rejected for the same reason 001 rejected it: SQLite's single-writer model makes races unlikely but not impossible, and the index is cheap insurance already proven in this codebase.

## FK indexing on `project_id`

- **Decision**: Add a plain (non-unique) index on `group_task.project_id` in addition to the two composite partial-unique indexes above.
- **Rationale**: Unlike some RDBMSes, SQLite does not automatically index foreign key columns. Every nested-route query (`list_active_group_tasks(project_id)`, the cascade-block's active-count check, `list_deleted_group_tasks_grouped_by_project()`) filters or groups by `project_id` first, so an index on it directly benefits every query this feature adds. The two composite indexes above both happen to lead with `project_id`, which SQLite's query planner can already use as a prefix for simple `project_id = ?` lookups on active rows — but soft-deleted rows (needed for the Deleted Items view and the cascade-block "any active" check, which scans regardless of the `deleted` flag before filtering) fall outside those partial indexes' `WHERE deleted = false` predicate, so a plain full-table index on `project_id` is still worth adding for those paths.
- **Alternatives considered**: Relying solely on the partial composite indexes — rejected, since they don't cover queries touching soft-deleted rows (the Deleted Items view's Group-task section explicitly needs those). No index at all — rejected, acceptable only at trivial scale and this feature's own SC-006 targets up to 200 Group-tasks per Project across potentially many Projects.

## Cascade-block: Project soft-delete rejected while active Group-tasks exist

- **Decision**: `soft_delete_project` gains a precondition check — before flipping `deleted = true`, query `EXISTS(SELECT 1 FROM group_task WHERE project_id = :id AND deleted = false)`; if true, raise the existing `ProjectValidationError` (reusing the type, not introducing a new exception) with a single message keyed under a generic field name (e.g. `"group_tasks"` or a non-field-specific key), e.g. `"Cannot delete: this project still has active group-tasks"`.
- **Rationale**: Reusing `ProjectValidationError` means the router's existing exception-to-response translation pattern extends with zero new plumbing — `_render_form_errors`-equivalent handling for the delete route renders the same class of error into `_page_errors.html`'s OOB fragment, exactly the mechanism 002 built and left empty for this purpose. Introducing a distinct exception type for this one new check would only add an extra `except` clause with no behavioral difference.
- **Alternatives considered**: Enforcing via the FK's `ON DELETE RESTRICT` and catching the resulting `IntegrityError` at the router — rejected per the same reasoning 001 rejected DB-only enforcement for uniqueness: translating a raw constraint violation into the specific, human-readable message FR-016 requires is fragile compared to an explicit pre-check, and soft-delete never touches the FK anyway (no row is ever removed, so `ON DELETE RESTRICT` would never even fire — the "delete" here is an `UPDATE`, not a `DELETE`). A cached `active_group_task_count` column on `project` — rejected as premature/derivable-on-demand state that must be kept in sync on every Group-task create/delete, for a query that's already cheap at this scale.

## Cross-cutting "resolve active parent Project or 404" check (FR-015a)

- **Decision**: One shared FastAPI dependency, `get_active_project_or_404(project_id: int, session: Session = Depends(get_session)) -> Project`, defined once in `app/routers/group_tasks.py` (thin wrapper around `services.get_active_project`, raising `HTTPException(404)` if `None`). Every one of the five nested Group-task routes — create (`GET`/`POST`), detail (`GET`), edit (`GET`/`PUT`), and delete (`DELETE`) — declares `project: Project = Depends(get_active_project_or_404)` in its signature instead of calling any lookup inline. The sixth place this check matters, the nested list embedded on `projects.py`'s own `GET /projects/{id}` route, calls the equivalent `services.get_active_project` lookup that route already performs for its own 404 handling — it is not a `group_tasks.py` route and has no dependency-injection relationship to this one, but produces the same outcome (404 on missing/deleted Project) via the same underlying service call.
- **Rationale**: FR-015a requires identical behavior across five distinct routes; a single dependency function referenced via `Depends(...)` in all five signatures is the only construction where the check textually exists in exactly one place and literally cannot drift if it's later changed (e.g., to add logging, or a different error message) — every call site updates automatically because there is only one definition. A plain function called manually at the top of each route body (viable, and what Project's own routes do today for their own not-found checks) still requires five separate call sites to each remember to call it and to do so before anything else in the route; FastAPI's dependency system removes even that residual risk by making the check part of the route's declared signature, enforced before the route body runs at all.
- **Alternatives considered**: A plain function called manually at the top of each route body — this was the original decision in this document; superseded because it still leaves five call sites that could individually drift (skip the call, call it late, or call a slightly different check) even though the helper itself is shared. Repeating the check's logic inline in every route with no shared function at all — rejected outright, exactly the duplication FR-015a's "every nested route" wording warns against.

## `/deleted` view placement and parent-Project lookup for already-deleted parents

- **Decision**: `/deleted` is a new top-level route (its own small module, `app/routers/deleted.py`, mounted in `main.py` alongside `projects.router` and `group_tasks.router`), not a route under `projects.py` — it no longer belongs to the `/projects` path at all per FR-025. It calls `services.list_deleted_projects()` (unchanged) and a new `services.list_deleted_group_tasks_grouped_by_project()`, the latter resolving each deleted Group-task's parent Project **by ID directly** (`session.get(Project, project_id)`, ignoring the parent's own `deleted` flag) rather than through `get_active_project`, since FR's acceptance scenario explicitly requires the parent's identity to still resolve correctly even after the parent Project is itself later soft-deleted.
- **Rationale**: This is the one place in the whole feature that must deliberately *not* gate on "is the parent active" — every live/mutating nested route does the opposite (FR-015a). Keeping this as a distinct, narrowly-scoped service function (rather than overloading `get_active_project_or_404` or `get_active_project` with an "ignore deleted" flag) keeps the "parent must be active" invariant simple and exception-free everywhere else, and makes this one read-only historical-display exception textually obvious at its call site.
- **Alternatives considered**: Storing a denormalized snapshot of the parent Project's serial_num/title on the Group-task row at the moment of the Group-task's own soft-delete — rejected as unnecessary duplication; the parent Project row is never hard-deleted (system-wide invariant), so a live lookup by `project_id` is always available and always accurate, with no staleness risk to guard against. Making `/deleted` a route nested under `/projects` with a redirect from `/projects/deleted` — rejected, FR-025 explicitly calls for updating the one existing link rather than preserving a back-compat alias, and no other consumer of the old URL exists to break.

## Validation shape reuse for Group-task (FR-008a, date ordering)

- **Decision**: `services.py` gains a private helper for Group-task validation, structurally identical in shape to `_validate_common_fields` (blank/whitespace + max-length checks on title/description, date ordering when both present) but not literally shared/extracted into a common function callable by both entities.
- **Rationale**: The two validation functions check the same rules but against different models with different max-length constants and different conflict-check signatures (Project's conflict checks take no `project_id` scope; Group-task's take one). Extracting a shared abstraction now, with exactly two call sites that happen to look alike today, would be speculative generalization ahead of a proven third use case (Task, in a future slice, may or may not need the identical shape) — duplicating this small, stable block of logic is cheaper to read and change independently than maintaining a shared helper's parameterization for two callers.
- **Alternatives considered**: A shared `_validate_title_and_description(title, description, max_title, max_desc)` helper parameterized by length limits — rejected for now per the reasoning above; revisit if/when the Task slice needs the identical shape a third time, at which point the pattern is proven rather than assumed.

## Migration strategy (unchanged approach from 001)

- **Decision**: `alembic revision --autogenerate` against the updated `models.py` (with `GroupTask` added), then manually reviewed before applying — same as 001's single migration. Expect autogenerate to correctly emit the `CREATE TABLE group_task` statement, the FK constraint to `project.id`, and the plain `project_id` index, but to require hand-verification (and likely hand-correction) of both partial composite unique indexes, consistent with 001's research.md noting autogenerate's known unreliability with partial/conditional indexes even in the single-column case.
- **Rationale**: Keeps the migration derived from the model by construction (avoiding hand-transcription drift) while acknowledging the one known gap in autogenerate's coverage, exactly as 001 already documented and handled.
- **Alternatives considered**: Hand-writing the full migration — rejected, same reasoning as 001 (duplicated effort, more drift risk) for the parts autogenerate does handle correctly (table shape, FK, plain index).
