## Known Issues / Watch
- **Intermittent malformed row HTML after delete — likely resolved, monitor (master-detail panes, Phase 6/create flow)**: During manual testing of delete, a row occasionally failed to disappear from the left-pane list after a successful delete, with the DOM showing signs of malformed `<tr>` structure (orphaned `<td>` elements outside a `<tr>`). This was never conclusively reproduced with clean evidence (no raw Network "Response" tab capture was taken at the time), so the original sighting itself is still unconfirmed — but a real, related bug was found and fixed since: `create_project`/`create_group_task` appended the new row via selector-targeted OOB swaps (`hx-swap-oob="beforeend:#...-list-body"`, briefly `innerHTML:#...-list-body`) — per htmx's own docs, "the encapsulating tag pair will be stripped for all strategies other than `outerHTML`," so this was silently dropping the `<tr>` wrapper and inserting bare `<td>` elements directly into the tbody on every create, which would produce exactly this symptom. All prior server-side diagnostics only checked the raw HTTP response text (well-formed as text), never actual client-side htmx DOM processing, which is why it wasn't caught sooner. `DELETE`'s own prior mechanism (per-row `hx-swap-oob="delete"`, an id-matching non-selector form) was independently confirmed safe from this specific tag-stripping bug, but had a separate real gap — it could only remove one row, with no way to show the "No projects yet." / "No group-tasks yet." placeholder when a delete emptied the list. Both create and delete now re-render the entire `<tbody>` as a single `hx-swap-oob="true"` (default outerHTML, tag-preserving) fragment, correct uniformly whether the list still has rows or just emptied out; the per-row edit/update case was already using this same safe single-row `hx-swap-oob="true"` form and needed no change. Given the original sighting's mechanism now lines up with a confirmed bug that's been fixed, treat this as likely resolved — but since it was never pinned down with hard evidence, keep watching for it. If it recurs, capture the raw Network "Response" tab output (not DOM inspector) immediately.
